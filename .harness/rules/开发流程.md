# 开发流程

## 本地运行 / 自证（完成前必做）

```bash
# 装依赖（首次）
pip install -r requirements.txt
playwright install chromium
cd lib && npm install        # Node 签名依赖（如缺）

# 跑起来（开发跳过 License 校验）
SKIP_LICENSE_CHECK=1 python run.py --port 8765
# 浏览器开 http://127.0.0.1:8765/
```

**禁止"写完即宣布 done"。** 按改动类型自证：
- 改 `app/` Python 代码 → `python -c "import app.main"` 能 import（无语法/循环依赖错），并 `ruff check` 通过。
- 改接口 → `curl` 打一次看响应，或起 server 在面板点一遍。
- 改前端模板 → 起 dev server 实际看页面。
- 改 `db.py`/`models.py` → 删本地 `data/app.db` 后重启，确认 `init_db` 迁移不报错。
- 改 `douyin_im.py` 签名/协议 → 用 `test_fetch_http.py` 思路拿真实 cookies 验签名链路。

失败先自己修 1–2 次再上报；无法验证就明说"因 XX 没跑"，绝不假装完成。单文件 <20 行 / 纯文档免验证。

## 测试（本项目：强制 TDD）

- 框架 **pytest**，测试放 `tests/`（按模块命名 `test_<module>.py`）。
- **先写测试再写实现**：红 → 绿 → 重构。新特性、修 bug 都先有一个能复现的失败测试。
- **覆盖率门槛 80%**，但重点压在核心逻辑：`douyin_im.py` 签名、`scheduler.py` 触发判定、`license.py` 验证、`crypto.py` 加解密、`trigger.py` 互斥锁与状态机。
- UI 模板、CLI 交互、一次性脚本（`fetch_security.py`）这类胶水可不强求单测，靠自证兜底。
- 抖音真实 HTTP 调用要 mock（`requests`/`douyin_im` 的网络部分），单测不依赖真实登录态和外网。
- 历史遗留的 `test_fetch_http.py` 是手动联调脚本不是单测，新测试不要学它的裸 `print` 风格。

## 任务分级

- **Light**（typo / 配置 / 单文件 <20 行）：直接做。
- **Medium**（bug / 小特性 / 1–3 文件）：TDD → 自证 → `/code-review`。
- **Heavy**（3+ 文件 / 跨模块 / 动 auth·license·加密·调度·抖音签名）：完整流程，改前先说清影响面。
  - 触碰 **license 签名、Fernet 密钥、CSRF/session、scheduler 触发逻辑、douyin 签名链** 一律按 Heavy 处理——这些错了会静默风控或漏洞。

## 提交规范（Conventional Commits）

沿用现有历史风格：`<type>(<scope>): <中文描述>`

```
feat(scheduler): 新增每日 cookies 体检
fix(notify): SMTP 按端口自动选协议
fix(scheduler): 改回 last_ran_date 判定
```

- type：`feat` / `fix` / `refactor` / `docs` / `chore`。
- scope：模块名（`scheduler` / `notify` / `api` / `trigger` / `debug`）。
- **提交/推送前先扫密钥**（见 `安全红线.md`）：`git diff --cached` 不得含 cookies、私钥、SECRET_KEY、SMTP 密码、真实 license。
- 只有用户明确要求时才提交/推送；当前在 `main`，推送会触发 CI。

## CI

push 到 `main` → GitHub Actions（`.github/workflows/`）：Cython 编译 `.py`→`.so` → 多阶段 Docker 构建 → 推 GHCR(private) + Docker Hub(public)，约 5–10 分钟。

```bash
gh run list --limit 5
gh run view <run-id> --log-failed | tail -50
```
